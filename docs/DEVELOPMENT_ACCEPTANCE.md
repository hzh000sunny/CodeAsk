# CodeAsk 开发验收阶段与证据基线

> 状态：Active
> 范围：整个 CodeAsk 项目
> 目的：统一每个版本、专项计划和阶段性收口的开发验收标准，避免只验证局部组件而遗漏真实产品链路。

## 1. 背景

CodeAsk 的核心能力不是单个接口、单个组件或单轮问答，而是一个可持续多轮工作的研发知识 Agent。任何验收如果只证明“数据保存了”“前端显示了”“工具被调用了”，都不足以说明 Agent 链路成立。

本项目以后必须区分以下概念：

| 容易混淆的现象 | 真实验收要求 |
|---|---|
| 前端能显示历史消息 | 模型下一轮请求真的带入了必要历史 |
| 右侧能显示行动轨迹 | 模型后续追问时能知道上一轮工具行动摘要 |
| 数据库保存了 turns | runtime 从数据库加载并正确转换为 LLM messages |
| 工具结果保存了 trace | 工具结果摘要受预算限制后进入模型上下文 |
| 单轮回答正常 | 同一会话连续追问仍能理解上一轮问题、回答和行动 |
| E2E 能跑通一次 | E2E 用例已沉淀为可重复测试通道，并记录执行条件 |

## 2. 项目级开发验收阶段

每个功能开发、重构、版本收口都必须按以下阶段验收。阶段可以按改动规模裁剪，但裁剪原因必须写入对应版本或计划文档。

### 2.1 需求与设计验收

- 明确本次改动影响的核心用户路径。
- 明确涉及的后端模块、前端页面、数据模型、LLM runtime、工具、RAG、权限或存储边界。
- 明确哪些能力是已实现、计划实现、显式不做。
- 涉及 Agent / LLM / RAG 时，必须写清楚模型应该看到什么上下文，以及哪些内容只用于 UI 或审计。
- 涉及版本规划时，必须更新对应版本的 `README.md`、PRD、Design、Plan 或 Acceptance Checklist。

### 2.2 单元与模块验收

- 后端新增逻辑必须有单元测试或集成测试覆盖核心分支。
- 前端组件必须有组件测试或 E2E 覆盖关键交互。
- Agent runtime 相关逻辑必须优先使用 fake / spy LLM 测试，直接断言实际发给模型的 `messages`、`tools` 和关键参数。
- 工具执行器、RAG 召回、上下文组装、压缩预算等模块必须验证输入输出结构，而不是只验证最终回答。

### 2.3 API 与持久化验收

- 验证 API 入参、响应、错误提示和状态码。
- 验证数据是否落库、是否按用户 / 会话 / 特性 / 仓库隔离。
- 验证页面刷新后数据能恢复。
- 验证删除、重命名、移动、清空等操作同时更新数据库、文件存储、索引和 UI 状态。
- 涉及会话时，必须同时验证 `session_turns`、`agent_traces`、附件 / Wiki / 报告引用。

### 2.4 Agent 连续会话验收

凡涉及默认会话、LLM runtime、工具调用、RAG、上下文压缩或行动轨迹的改动，必须额外通过以下验收：

- 同一会话第二轮提问时，模型上下文包含最近用户消息和助手回答。
- 同一会话第二轮提问时，模型上下文包含上一轮关键工具行动摘要。
- 用户追问“你刚刚是否查过代码 / 用了什么证据 / 上一轮做了什么”时，CodeAsk 能基于真实历史回答。
- CodeAsk 能区分：
  - 是否调用了代码相关工具；
  - 是否实际读取了源码文件；
  - 是否基于源码证据回答。
- 页面刷新后继续追问，模型仍能基于历史上下文回答。
- 前端历史恢复、后端模型上下文恢复、行动轨迹恢复必须分别验收，不能互相替代。
- 上下文历史和工具行动摘要必须受预算限制，不允许把完整 trace JSON 或超大工具结果直接塞进模型。

### 2.5 E2E 与真实环境验收

- 涉及前端核心流程的改动，必须有 Playwright 或等价浏览器 E2E。
- 涉及 Agent / LLM / RAG / 工具调用的改动，必须保留 live E2E 通道；默认可以跳过真实 LLM，但必须能通过显式环境变量开启。
- live E2E 如果共享同一套 LLM 配置、仓库注册状态、会话数据库或临时数据目录，默认必须串行执行；只有在隔离边界被明确验证后，才能恢复并行。
- 涉及登录、权限、数据隔离的改动，必须验证用户身份、数据归属和刷新后的持久化行为。
- 真实 LLM 验收必须记录模型、配置来源、会话 id、测试问题、工具触发情况和结论。
- 临时手动调试不能替代长期测试通道；验证出有价值的流程后，应沉淀到 `frontend/e2e/`、后端集成测试、`evals/` 或版本验收文档中。

### 2.6 回归与收口验收

版本或阶段收口前必须记录：

- 后端测试命令和结果。
- 前端测试命令和结果。
- E2E / live E2E 测试命令、是否执行、跳过原因和剩余风险。
- `git diff --check` 结果。
- 未完成项和阻塞项。
- 对用户可见行为是否仍符合 PRD。

## 3. Agent / LLM 专项验收矩阵

涉及 Agent 的每次开发都必须维护以下矩阵，至少在版本 `plans/acceptance-checklist.md` 中体现。

| 验收项 | 最低证据 |
|---|---|
| 单轮普通问答 | fake LLM 或真实 LLM 会话记录 |
| 多轮上下文追问 | spy LLM 断言第二轮 messages 包含上一轮 user / assistant |
| 工具行动可追问 | spy LLM 或 live E2E 断言上一轮 tool summary 进入上下文 |
| 工具调用由模型决策 | 不使用关键词硬拦截；测试只统计偏差 |
| 工具优化不做业务特判 | 正向测试证明通用质量提升，反向测试证明没有硬编码业务词 / 仓库名 / 固定路径 |
| 工具结果预算 | 单元测试断言超大 payload 被真实裁剪 |
| RAG 片段注入 | 测试断言注入 snippet / evidence ref，不注入全文 |
| 刷新后继续追问 | 浏览器 E2E |
| 删除 / 清理 | 浏览器 E2E + 存储检查 |
| 错误反馈 | 失败弹窗或结构化错误，不静默失败 |
| 文档同步 | PRD / Design / Plan / Acceptance Checklist 更新 |

## 4. 验收证据格式

文档中记录验收结果时，必须尽量使用下面的格式：

```text
验收项：
状态：通过 / 未通过 / 未执行 / 不适用
证据：
- 测试命令：
- 测试文件：
- 会话 id：
- 模型配置：
- 关键断言：
剩余风险：
```

不允许只写“已验证”“应该可以”“手动看过”。如果因为环境限制没有执行，必须写明未执行原因和风险。

## 5. 当前已暴露的共性问题

以下问题不是单个 bug，而是验收体系的共性缺口，所有后续版本都要规避：

- 把 UI 能恢复历史误认为模型能看到历史。
- 把 trace 能展示误认为模型能追问上一轮工具行动。
- 把单轮问答基线误认为多轮 Agent 能力。
- 只检查最终回答，不检查 LLM 请求 messages。
- 只做临时手工调试，没有沉淀长期 E2E 通道。
- 过早开发上下文压缩，而没有先验证上下文装配是否正确。
- 用工具层 hardcode 制造“看起来答对”的结果，破坏“模型基于上下文决策”的产品原则。

## 6. 工具优化质量边界

所有涉及 Agent 工具、RAG adapter、代码检索、Wiki 检索、报告检索、附件读取、行动轨迹和上下文预算的优化，都必须遵守以下边界：

```text
工具只做执行质量、边界校验、结果结构化、预算控制、错误可解释。
工具不做业务判断。
```

允许的工具优化：

- 输入 schema 校验、权限校验、路径校验、版本边界校验和写操作确认。
- 通用鲁棒性增强：大小写不敏感、分隔符归一、长 query 拆词 fallback、结果去重、分页、超时、预算裁剪。
- 可执行引用补齐：Wiki / 报告 / 附件 / 代码结果必须尽量提供稳定 id、路径、行号、版本和原始结果引用。
- 错误可解释化：失败应尽量返回可恢复的错误类型和 recovery hint，而不是泛化 `internal_error`。
- UI / trace 折叠：可以降低噪音，但展开后必须能看到原始参数、结果、错误和审计引用。

禁止的工具优化：

- 不得把业务自然语言写成固定映射，例如 `电子宠物 -> buddy`、`sqlite -> schema.prisma`、`RAG -> contextTexts`。
- 不得按题型强制禁止或强制触发工具调用。
- 不得返回“知识足够 / 不足”“无需查代码”“应该读取某文件”等流程结论。
- 不得为了减少 UI 噪音隐藏失败。
- 不得过度压缩到模型丢失证据引用、错误类型、版本信息和恢复建议。

每次工具优化必须补充：

- 正向测试：证明通用执行质量提升。
- 反向测试：证明没有针对业务词、仓库名、固定路径或测试样例 hardcode。

## 7. v1.0.2 的强制补充要求

v1.0.2 在收口前必须补齐：

- 连续会话上下文进入模型的 spy LLM 测试。
- 上一轮工具行动摘要进入模型的 spy LLM 测试。
- 用户追问“你刚刚是否查过代码”的 live 或 E2E 验收。
- 刷新后继续追问的浏览器 E2E 验收。
- `plans/acceptance-checklist.md` 中明确标记所有未完成项，不能把“计划中”写成“已完成”。
