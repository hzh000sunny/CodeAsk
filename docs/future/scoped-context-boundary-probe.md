# 特性边界探测与上下文隔离

> 状态：Draft
> 版本归属：待定
> 主题：在 Agent 会话中，用临时全量特性 RAG 帮助模型判断问题边界，并在判断动作结束后丢弃污染上下文。

## 1. 背景

CodeAsk 的产品定位不是传统 LLM Wiki，而是面向垂直领域的问题定位工作台：

- 普通问题应回归自然问答，不应该每次都强行走完整定位链路。
- Wiki、问题报告、代码仓库、会话附件都是模型可参考的上下文，而不是后端写死的判断规则。
- 当用户不知道问题属于哪个特性时，系统应该帮助模型判断可能的特性边界。
- 当知识不足时，模型可以基于上下文决定是否继续读取 Wiki、报告、附件或代码。

当前已确认的原则是：**是否属于某个特性、是否跨特性、是否需要查询代码，都应由模型基于足够上下文自主判断**。工具层只负责提供候选信息、执行工具、校验权限和记录审计，不应把业务语义写成硬编码特判。

但这带来一个新的上下文问题：

如果为了让模型判断特性边界，把所有特性的 RAG 召回信息一次性注入长期对话上下文，这些候选数据会持续污染后续回答。模型可能在某一轮形成边界假设后，仍被无关特性的内容干扰，导致错误归因、错误报告绑定或无意义工具调用。

因此需要引入“临时边界探测上下文”的设计。

## 2. 核心目标

### 2.1 要解决的问题

1. 用户提问时未显式指定特性，但知识库中可能存在相关线索。
2. 相关线索可能不在特性名称或描述里，而在该特性的 Wiki、报告、附件摘要或代码仓库说明里。
3. 模型需要看到足够的跨特性候选信息，才能形成当前轮次的问题边界假设。
4. 用于判断边界的全量候选上下文，不应该在判断动作完成后继续污染回答上下文。
5. 已形成的边界只能作为“当前假设”，不能变成后端锁死的会话范围。
6. 长对话中用户可能换题、跨特性追问、纠正模型判断，模型必须能自主决定是否重新判断边界。

### 2.2 不要解决的问题

本设计不直接实现完整向量库升级，也不替代未来 RAG 服务：

- 不要求在本阶段实现 LanceDB 全量向量管线。
- 不要求引入 LangChain。
- 不要求一次性重做 Wiki、报告、附件、代码的索引系统。
- 不要求把 Agent runtime 改成固定状态机。

它只定义一个未来能力方向：**在模型需要判断边界时提供足够候选上下文，在该判断动作结束后只保留精简边界假设和审计记录。**

## 3. 设计原则

### 3.1 模型决策优先

边界判断、是否继续沿用边界、是否扩大边界、是否重新判断边界，都必须交给模型：

- 后端可以召回候选特性、候选 Wiki、候选报告、候选仓库。
- 后端可以限制最大数量、截断内容、去重来源、标注来源。
- 后端不应该写“关键词 A 必定等于特性 B”的特判。
- 后端不应该因为某个关键词命中，就直接决定查询代码或绑定报告。
- 后端不应该因为上一轮判断过某个特性，就在后续会话中强制只带这个特性。
- 后端不应该用固定规则决定“本轮必须重新判断边界”或“本轮不能重新判断边界”。这些策略应通过上下文说明交给模型决策。

### 3.2 上下文分层

一次用户请求不应该只有一个不断膨胀的上下文，而应拆成不同用途的上下文帧：

```text
base_context
  用户消息、历史摘要、最近对话、已确认约束

boundary_probe_frame
  全特性候选信息、跨特性 RAG 召回、候选 Wiki/报告/仓库摘要
  只用于判断问题边界

response_frame
  base_context + 当前边界假设 + 可用工具说明 + 必要的精简上下文
  用于生成真正给用户的回答，并让模型决定是否继续查证、扩大范围或重新判断边界

audit_trace
  完整记录 boundary_probe 使用了哪些候选来源、模型如何判断
  供前端 Agent 行动轨迹和后端排查使用，不注入后续模型上下文
```

这里的“备份 / 恢复上下文”不应理解为修改同一份消息数组后再回滚。LLM 调用本质上是无状态请求，更合适的实现方式是：**显式构造不同的 message frame**。边界探测调用结束后，不把 `boundary_probe_frame` 原文带入下一次回答，只把结构化边界假设、证据摘要和不确定性写入 `response_frame`。

### 3.3 临时探测，不污染后续对话

边界探测完成后，长期上下文只保留“当前假设”和“模型可重新判断的规则说明”：

- 可能相关的特性列表，明确标注为当前假设。
- 主特性和交叉特性判断，明确标注置信度和可被后续对话推翻。
- 置信度和不确定原因。
- 用于后续工具默认 scope 的最小必要信息，但只能作为默认建议。
- 用户需要确认的问题。
- 模型何时应该考虑重新判断边界的上下文规则。

长期上下文不保留：

- 全量候选特性目录。
- 大量无关 Wiki 片段。
- 未命中的报告摘要。
- 与当前问题无关的代码仓库说明。

关键约束：

- 丢弃的是“全量特性判断动作中的污染上下文”，不是丢弃模型重新判断边界的能力。
- 已有边界假设不是会话级锁定状态。它只能帮助模型减少重复判断，不能限制模型后续重新选择范围。
- 后续是否需要再次执行边界探测，应由模型基于用户新问题、上下文变化和工具说明自行决定。

## 4. 边界探测输入

未来边界探测前，应尽量给模型提供足够但受控的候选信息。

候选信息可以包含：

- 所有特性的名称、描述、别名、owner、更新时间。
- 每个特性的知识库摘要或 top chunks。
- 每个特性的问题报告摘要、标题、根因、验证状态。
- 每个特性关联的代码仓库名称、描述、默认分支、最近更新时间。
- 当前会话已上传的附件名称、重命名名、摘要。
- 当前用户问题和最近若干轮对话。

候选信息必须带来源 metadata：

```text
source_type: feature | wiki | report | attachment | repo
feature_id
feature_name
node_id / report_id / repo_id
title
path
snippet
score
updated_at
```

## 5. 边界探测输出

边界探测应输出结构化结果，供后续上下文构造、工具默认 scope 和报告默认绑定参考。

建议输出字段：

```json
{
  "intent_type": "general_answer | feature_qa | incident_diagnosis | code_question | report_generation | unclear",
  "primary_feature_id": 6,
  "related_feature_ids": [6],
  "feature_confidence": "high | medium | low",
  "reason": "用户提到小米病情，Wiki 召回命中小米病历。",
  "needed_clarification": null,
  "is_hypothesis": true,
  "may_need_reprobe_when": [
    "用户切换主题",
    "用户提到新的特性、仓库、模块或业务对象",
    "当前回答缺少证据",
    "用户纠正当前特性判断"
  ],
  "recommended_context_scope": {
    "wiki": [6],
    "reports": [6],
    "repos": []
  },
  "should_continue_without_clarification": true
}
```

注意：这个结果仍然是模型判断，不是工具层硬规则。后端只能把它作为下一轮 `response_frame` 的边界假设和工具默认 scope 建议。模型在后续每一轮都可以选择沿用、扩大、缩小、重做或放弃这个假设。

## 6. 后续回答上下文

边界探测后，`response_frame` 应注入的是“当前边界假设 + 模型决策规则”，而不是后端收窄后的唯一事实范围：

- 用户原始问题。
- 最近对话摘要。
- 当前暂定的特性边界假设。
- 与当前问题直接相关的精简 Wiki / 报告 / 附件 / 仓库摘要。
- 工具可用性说明。
- 明确告诉模型：如果用户换题、当前证据不足、出现新特性线索或可能存在交叉特性，可以重新触发边界探测或扩大工具范围。
- 如果边界不确定，明确告诉模型优先和用户自然沟通确认。

示例：

```text
你正在回答用户问题。上一阶段形成的当前边界假设如下：
- 小米（置信度 high）：Wiki 命中“小米病历”，包含病情、治疗记录和肿瘤相关信息。

这是当前假设，不是锁定范围。你可以优先参考该特性的 Wiki 和报告。
如果用户换题、出现新的特性线索、证据不足、可能跨特性，或你认为当前假设可能错误，应先说明原因，并决定是否重新进行边界探测、扩大检索范围或向用户确认。
不要把边界探测阶段的其他候选内容当作已确认事实。
```

这段规则应作为 prompt / context policy 注入给模型，而不是在后端写死为 if/else。

## 7. 与工具调用的关系

### 7.1 Wiki / 报告工具

当前边界假设可以作为 Wiki / 报告工具的默认 scope，但不能变成唯一 scope。

如果模型认为可能是交叉特性，可以让工具读取多个特性范围。

如果模型认为边界不确定，可以先向用户提问，也可以读取低成本的 Wiki 摘要帮助确认。

如果模型认为用户已经换题，或当前问题与既有边界假设无关，应允许模型重新执行边界探测。

### 7.2 代码工具

代码工具的默认范围可以来自边界假设中的特性关联仓库。

如果用户显式要求查询某个仓库，即使该仓库没有关联特性，也允许查询。

如果模型无法确认仓库边界和版本：

- 默认允许读取代码。
- 但应优先基于当前已配置仓库和默认分支。
- 如果用户问题对版本敏感，应自然询问分支、commit、版本号。

### 7.3 问题报告

报告默认绑定特性应优先参考当前会话的最新边界假设，而不是使用旧报告绑定、候选目录顺序或 broad catalog 首项。

重复生成报告时：

- 应基于当前会话内容重新判断边界。
- 已存在报告的旧 feature 只能作为弱参考。
- 如果用户在弹窗中手动改了特性，保存时以用户选择为准。
- 如果会话内容显示用户已经换题或跨特性，报告生成应让模型先形成新的报告范围建议，而不是继承早期边界。

### 7.4 后端职责边界

后端可以做：

- 构造 `base_context`、`boundary_probe_frame`、`response_frame`。
- 提供候选召回、工具 schema、权限校验、token 预算、来源去重和审计记录。
- 根据模型输出的结构化结果更新当前边界假设。
- 在报告生成、工具默认 scope 中使用模型给出的假设作为建议。

后端不应该做：

- 写死某类问题必须查 Wiki、必须查代码或必须绑定某个特性。
- 根据关键词直接把用户问题归入某个特性。
- 因为上一轮命中某个特性，就禁止模型访问其他特性。
- 用固定规则决定“当前轮不需要重新判断边界”。
- 把边界假设当成长期不可变的会话绑定。

## 8. 与上下文压缩的关系

边界探测结果可以进入长期摘要，但只能进入精简、可推翻的形式：

```text
本会话近期问题主要关联“小米”特性；依据是 Wiki 命中“小米病历”和用户多次询问病情变化。该判断是当前边界假设，如果用户换题或出现新线索，应重新评估。
```

不能把边界探测阶段的全量 RAG 候选放入长期摘要。

当上下文接近预算上限时，压缩策略应保留：

- 用户目标。
- 当前边界假设及其置信度。
- 已读取过的关键证据。
- 仍未解决的问题。
- 模型可重新判断边界的规则。

压缩策略应丢弃：

- 已经淘汰的候选特性。
- 无关召回片段。
- 重复工具调用结果。
- 被后续判断否定的临时线索。

压缩后的摘要不能把“某轮边界判断”改写成“会话永久绑定特性”。

## 9. 审计与前端展示

虽然 `boundary_probe_frame` 不进入后续模型上下文，但必须可审计。

Agent 行动轨迹中应能看到：

- 本轮是否执行了边界探测。
- 探测候选来自哪些来源。
- 模型判断的主特性、交叉特性和置信度。
- 哪些候选被丢弃。
- 为什么后续工具 scope 建议优先使用某些特性或仓库。
- 当前边界假设是否沿用、扩大、缩小、重做或放弃。

展示上应避免把所有候选内容铺满页面，可以采用：

- 卡片摘要默认折叠。
- 点击后查看完整候选来源。
- 明确标注“边界探测临时上下文，未带入后续回答”。
- 明确标注“当前边界是假设，不是锁定范围”。

## 10. 验收场景

未来进入版本开发时，至少需要覆盖以下 E2E 场景：

1. **普通基础问答**
   - 用户问 Python list 和 tuple 区别。
   - 模型可以直接回答。
   - 不应因为存在 Wiki 或代码仓库就强行进入定位链路。

2. **特性名称命中**
   - 用户问“小米什么时候得的肿瘤”。
   - 模型应能基于候选上下文形成“小米”边界假设。
   - 后续回答优先参考小米相关 Wiki / 报告，但不能锁死后续会话范围。

3. **Wiki 内容命中但特性名未命中**
   - 用户问题不包含特性名称，但命中某个特性 Wiki 内的业务关键词。
   - 模型应能通过候选 Wiki 判断相关特性。

4. **交叉特性**
   - 用户问题同时涉及两个特性的知识或报告。
   - 输出 `related_feature_ids`，并允许工具在两个特性范围内检索。

5. **长对话换题**
   - 同一个会话先问“小米病情”，随后问“claude-code 如何调用 grep”。
   - 模型应识别新问题与旧边界假设不同，可以重新判断边界或直接按显式仓库意图查询。
   - 不应因为早期命中“小米”而限制后续回答。

6. **边界判断失误后的纠正**
   - 模型早期错误判断特性。
   - 用户纠正后，模型应能放弃旧假设，重新构造后续上下文。
   - 旧的全量候选污染不应进入长期摘要。

7. **显式仓库查询**
   - 用户要求“查询 claude-code 仓库如何调用 grep”。
   - 即使仓库未绑定特性，也允许基于显式仓库意图查询代码。

8. **边界不确定**
   - 用户问题过短或缺少关键上下文。
   - 模型应自然追问，而不是后端硬塞默认特性。

9. **报告默认绑定**
   - 会话中已多次命中某特性。
   - 生成报告弹窗默认选择该特性。
   - 旧报告的错误绑定不能污染新的默认选择。

10. **上下文污染检查**
   - 边界探测阶段召回了多个无关特性。
   - 后续回答不得引用已淘汰特性的内容。
   - 长期摘要中不应出现无关候选内容。

## 11. 待设计问题

正式排入版本前，还需要继续明确：

1. 如何通过 prompt / tool policy 让模型自行判断本轮是否需要边界探测，而不是由后端固定每轮执行或固定条件触发。
2. 边界探测的 token 预算和候选数量上限。
3. 候选特性的初筛方式：关键词、轻量 embedding、已有本地 RAG 服务或混合检索。
4. `boundary_probe_frame` 的 prompt 模板和结构化输出校验策略。
5. 边界结果如何写入 session state、report prepare、tool scope 和 long-term summary。
6. 前端 Agent 行动轨迹如何展示“临时上下文被丢弃”这个事实。
7. 如何避免模型在边界探测阶段过早决定“需要查代码”，而忽略普通问答能力。
8. 如何在 prompt 中表达“边界是假设，可被模型自主重评”，同时不让模型每轮无意义地重复探测。
9. 如何把“继续沿用 / 扩大 / 缩小 / 重做 / 放弃边界”的选择交给模型，而不是后端策略。

## 12. 当前建议

该能力适合放在 v1.0.2 之后的 Agent runtime 优化版本中，不建议继续塞进 v1.0.2。

原因：

- v1.0.2 已经涉及模型决策、工具 scope、报告生成、上下文预算和 E2E 验收，继续重塑核心上下文帧风险较高。
- 该能力会影响 Agent runtime 的消息构造、工具默认范围、报告绑定和行动轨迹展示，需要单独设计和验收。
- 它与未来 LanceDB / LangChain / RAG 服务升级强相关，但可以先用当前轻量召回实现接口雏形。

推荐推进顺序：

1. 先收口 v1.0.2 中已明确的会话、工具、报告和 E2E 问题。
2. 在后续版本中实现 `boundary_probe_frame` 和 `response_frame` 的上下文隔离，并把边界重评规则注入给模型。
3. 再逐步替换候选召回层，接入更完整的 LanceDB / RAG 服务能力。
