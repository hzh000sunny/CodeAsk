# 问题定位报告规则

> 范围：跨版本规则
> 状态：Active

本文定义 CodeAsk 中“问题定位报告”的稳定产品规则。

本规则同时约束：

- 会话中的“生成报告”行为
- Wiki 中的问题定位报告内容形态
- 报告标题命名方式
- 后续报告检索、验证、回流与排序的基础前提

当版本级 PRD、SDD 或实现计划涉及问题定位报告时，应引用本文，而不是重新发明一套局部规则。

## 1. 报告的本质

问题定位报告不是聊天记录副本，也不是会话摘要。

它是一份面向研发知识沉淀的正式 Markdown 文档，目标是：

- 让后续读者快速理解问题背景、定位过程和当前结论。
- 明确区分已确认事实、推断结论和待补充信息。
- 让报告可以进入后续知识检索，而不是只在当前会话中存在。

因此，AI 生成报告时的目标应是“成文”，不是“整理聊天记录”。

## 2. 标题规则

标题必须满足以下强约束：

```text
YYYY-MM-DD 问题描述
```

规则说明：

- 日期取**生成报告当天**。
- `问题描述` 由 AI 基于当前上下文先行生成。
- 用户允许手动修改 `问题描述` 部分。
- 无论 AI 还是用户修改，最终保存前都必须满足该标题格式。
- 不允许默认使用会话标题作为最终报告标题。

该规则是强约束，主要用于：

- 时间排序
- 时间查询
- 后续检索和管理一致性

## 3. 正文生成规则

报告正文由 AI 自主组织，不强制固定章节名。

系统可以给 AI 提供写作参考，但不能把章节标题写死为必须输出的模板。

AI 应优先根据上下文，自主组织出最合适的文档结构。

## 4. 生成方式与上下文规则

生成报告时，系统必须把“报告写作要求”连同当前会话上下文一起发给 AI，由 AI 自主生成默认标题和正文。

这里的上下文至少应包含：

- 当前会话中的用户提问与关键回答
- 已沉淀的工具行动摘要或调查轨迹
- 已确认的证据、附件、Wiki、报告、代码线索
- 当前可推断的特性上下文
- 报告写作约束本身

不允许的实现方式：

- 仅靠后端字符串模板拼正文
- 把最近几轮聊天记录直接拼成“报告”
- 不把报告规则告诉 AI，只让 AI 在无约束状态下自由输出

报告生成是独立的“成文任务”，不是把聊天记录换个标题保存。

### 4.1 AI 输出协议与解析容错

实现层可以要求 AI 先输出机器可解析结构，例如：

```json
{
  "title_description": "问题描述",
  "body_markdown": "# 正式报告正文"
}
```

但模型输出不能被视为永远严格合法 JSON。后端解析时必须遵守以下规则：

- 严格 JSON 解析优先，成功时直接使用。
- 支持从 Markdown 代码块中提取 JSON。
- 支持修复 JSON 字符串里的裸换行、回车和制表符。
- 当 `body_markdown` 中包含 Markdown 正文常见的未转义半角双引号时，应做固定 schema 的容错提取，尽量恢复 `title_description` 和 `body_markdown`。
- 当 LLM 输出因报告过长被截断，导致 JSON 对象或 Markdown fenced code block 未闭合时，如果固定 schema 中已经出现可恢复的 `title_description` 或 `body_markdown`，后端仍应尽量恢复这两个字段。
- 如果模型已经给出 `title_description`，不得因为正文 JSON 转义问题把标题兜底成 `未命名问题`。
- 如果模型已经给出可恢复的 `body_markdown`，不得把原始 JSON 或 JSON 代码块直接保存为报告正文。

该容错只服务于报告草稿的固定输出结构，不能扩展成任意 JSON 猜测器。确实无法恢复时，才允许使用 `未命名问题` 和待补充正文兜底，并应保留错误日志供排查。

报告生成的输出 token 上限不能过低。实现层应为报告草稿使用明显高于普通标题/摘要生成的输出预算，并在解析失败时记录足够信息，便于确认是模型未按协议返回、输出被截断，还是解析器缺少容错。

报告草稿生成可能触发较长时间的 LLM 调用，因此实现层必须按异步任务处理：

- 前端发起“准备报告”时，后端应立即返回 `request_id` 和 `running` 状态。
- 前端随后使用 `request_id` 轮询任务状态，直到得到 `succeeded + draft` 或 `failed + error`。
- 前端轮询不应采用过密固定间隔。默认策略为：启动后立即查一次，前 30 秒每 2 秒查一次，30 秒后每 5 秒查一次，总等待时间 10 分钟。
- 不允许把完整 LLM 生成过程绑定在一个长时间不返回的同步 HTTP 请求上。
- 任务状态必须按会话隔离，不能仅凭 `request_id` 跨会话读取草稿。
- 失败结果仍必须按 `docs/rules/ui-feedback.md` 使用页面中央阻断式弹窗展示。

## 5. 写作覆盖面要求

虽然不固定章节名，但报告正文应尽可能覆盖以下信息面：

- 问题背景
- 当前现象或触发条件
- 调查或定位过程
- 分析逻辑或判断依据
- 当前根因判断
- 解决建议或下一步建议
- 总结
- 参考资料

允许情况：

- 多个信息面合并为一个章节。
- 某些信息面使用不同命名。
- 某些会话因为证据不充分，只能覆盖部分内容。

不允许情况：

- 直接把聊天记录逐段复制成报告正文。
- 正文主体只是“用户说了什么 / AI 说了什么”的会话流水账。

## 6. 证据不足时的生成策略

即使当前会话尚未完成完整定位，也允许生成报告草稿。

但此时正文必须明确表达：

- 哪些内容是已确认事实。
- 哪些内容是当前推断。
- 哪些问题仍未确认。
- 还需要补充哪些信息或证据。

不允许把证据不足的草稿写成“已经确认根因”的口吻。

## 7. 参考资料规则

参考资料一节不固定为死板格式，也不限制只能列出某一类来源。

由 AI 根据当前上下文自主组织。

但前提仍然是：

- 来源应尽量来自当前上下文中的真实证据或相关资料。
- 不应凭空编造不存在的参考项。

## 8. 会话与报告绑定规则

当报告来源于会话生成时，必须满足以下关系约束：

1. 一个会话最多只能绑定一篇问题定位报告。
2. 第一次生成时创建报告草稿。
3. 同一会话再次生成时，必须覆盖更新原来的那篇报告，而不是新建第二篇。
4. 会话删除时，不删除该报告。

唯一关系的目的不是保留“生成历史”，而是保证：

- 会话视角下只有一个当前报告出口
- 报告列表不会因为重复生成而出现大量近似副本
- 用户能在原报告上持续补充、验证和沉淀

删除会话后，报告仍应保留原始来源痕迹，例如原会话 id、来源类型和生成时间，便于后续追溯。

## 9. 特性默认选择规则

会话触发生成报告时，系统应尽量根据当前会话上下文预判最相关特性，并作为默认选项提供给用户。

规则如下：

1. 如果会话中已经出现明显确认的特性，应默认选中该特性。
2. 如果存在多个交叉特性，应默认选中关联度最高、置信度最高的那个。
3. 只有在系统确实无法推断会话属于哪个特性时，才要求用户手动选择。
4. 用户仍然可以手动改选特性，但默认值不应退化为“永远让用户自己选”。

这里的“默认选中”是为了减少操作负担，不代表后端替用户做不可逆结论。

## 10. 用户编辑规则

生成报告时：

- AI 先给出默认标题和正文。
- 用户可以修改标题中的“问题描述”部分。
- 用户也可以在后续页面继续编辑正文。

用户可编辑并不改变标题格式规则：最终标题仍必须满足 `YYYY-MM-DD 问题描述`。

## 11. 对实现层的直接要求

任何版本在实现“生成问题定位报告”时，至少需要满足：

1. 生成目标是正式报告，而不是聊天记录整理。
2. 标题默认由 AI 生成，但必须自动带上当天日期前缀。
3. 标题允许用户修改问题描述部分，但最终格式必须校验。
4. 正文结构给 AI 参考，不固定章节名。
5. 证据不足时允许生成草稿，但必须显式写出未确认项和待补充项。
6. 报告生成要求必须通过上下文传给 AI，而不是靠纯模板拼接。
7. 会话来源报告必须满足“一会话一报告”，重复生成更新原报告。
8. 会话删除不能级联删除该报告。
9. 报告生成弹窗应尽量默认选中当前最相关特性，而不是默认留空。
10. 报告草稿准备必须使用异步任务接口，避免代理、浏览器或网关在长响应结束时返回 503。
11. 报告草稿解析必须优先使用严格 JSON，并对模型常见 JSON-like 输出做有限容错；不能因正文中裸双引号、裸换行、输出截断等可恢复格式问题，把已生成标题保存为 `未命名问题` 或把原始 JSON 保存成正文。
12. 每次修复报告解析问题，都必须补充最小回归测试，覆盖具体坏样本，而不是只靠人工重新生成验证。
