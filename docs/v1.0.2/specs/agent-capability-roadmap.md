# CodeAsk Agent 后续能力路线

> 日期：2026-05-07
> 状态：草稿，作为 v1.0.2 之后的版本规划边界
> 范围：明确 CodeAsk 如何借鉴 Claude Code 的 Agent 能力，但保持研发知识定位产品的边界

## 1. 记录目的

本文件记录 v1.0.2 之后的 Agent 能力演进方向，避免后续开发时把两个问题混在一起：

- CodeAsk 应该学习 Claude Code 的哪些 Agent harness 能力。
- CodeAsk 不应该直接变成通用 coding agent。

当前结论是：

```text
CodeAsk 可以实现 Claude Code 同等级别的 Agent harness。
CodeAsk 不应该在短期内实现 Claude Code 同等范围的通用 coding agent。
```

CodeAsk 的产品定位仍然是：

```text
研发知识定位 Agent
= 聊天 + Wiki + 报告 + 附件 + 代码只读检索 + 证据链 + 报告沉淀
```

而不是：

```text
通用代码 Agent
= 聊天 + 文件编辑 + Bash + 自动改代码 + 多 agent + worktree + MCP
```

## 2. 能力分层

### 2.1 必须实现的 Agent harness 能力

这部分是 v1.0.2 的核心，必须优先完成：

- 正常多轮聊天，不走固定后端调查流程。
- 模型根据上下文决定下一步动作。
- 工具注册表。
- 工具 schema 校验。
- 工具执行器。
- 只读工具默认可调用。
- 写操作需要确认。
- 工具错误结构化返回给模型。
- 工具结果进入上下文继续推理。
- 上下文预算、截断、摘要。
- 行动轨迹和审计记录。
- `ask_user` 作为模型可调用工具。
- Wiki、报告、附件、代码读取的工具化能力。

这部分完成后，CodeAsk 才具备正确的 Agent 底座。

### 2.2 分阶段借鉴的工程增强能力

这部分有价值，但不应该全部塞进 v1.0.2：

- 只读工具并发执行。
- 复杂上下文压缩。
- 工具结果去重。
- 长会话记忆。
- skill / 分析策略按需发现和加载。
- 任务列表 / investigation plan 辅助推理。
- 后台任务。
- 多 agent / subagent。
- MCP 扩展。
- worktree 隔离。
- 权限策略细分。
- 代码版本、分支、commit 的严谨管理。

这些能力必须根据 CodeAsk 的垂直场景重新设计，而不是直接照搬。

### 2.3 暂时不追求的通用 coding agent 能力

短期内不应该作为 CodeAsk 的主线目标：

- 任意 Bash 执行。
- 自动修改代码。
- 自动创建 patch。
- 自动跑测试并修复。
- 文件写入。
- notebook 编辑。
- shell 权限弹窗。
- 本地终端 TUI 交互。
- 通用开发任务 agent 化。

这些能力会显著增加安全风险和产品复杂度，也会让 CodeAsk 偏离“研发知识问答和问题定位”的核心定位。

## 3. 推荐版本路线

### 3.1 v1.0.2：Agent harness 修正

目标：

```text
把当前错误的固定调查链路替换为正常聊天优先的工具化 Agent runtime。
```

必须完成：

- 正常聊天 runtime。
- tool calling loop。
- Wiki / 报告 / 附件 / 代码只读工具。
- `ask_user`。
- Agent 行动轨迹。
- mock LLM 测试。
- 真实 LLM 端到端验证。

明确不做：

- 自动改代码。
- Bash。
- 多 agent。
- worktree。
- MCP。
- 企业级权限系统。

### 3.2 v1.0.3：上下文和记忆能力增强

目标：

```text
让 CodeAsk 更像长期协作的研发助手，而不是每轮重新开始的问答工具。
```

候选能力：

- 会话摘要。
- 附件摘要缓存。
- 用户补充事实提取。
- 特性候选记忆。
- 代码版本记忆。
- 工具结果去重。
- 大上下文压缩。
- 历史报告证据召回优化。
- 用户口语描述与附件、Wiki、报告、代码证据之间的映射增强。

设计原则：

- 记忆是辅助上下文，不是后端强制判断。
- 记忆必须可追踪来源。
- 记忆不能覆盖用户当前轮明确输入。

### 3.3 v1.0.4：任务和调查计划能力增强

目标：

```text
让模型在复杂问题中自己维护轻量调查计划，但不能恢复成后端固定状态机。
```

候选能力：

- `todo` / `investigation_plan` 作为模型可调用工具。
- 复杂问题时模型自己列出调查步骤。
- 用户可以看到、调整、取消计划。
- 每一步由模型决定，不由后端状态机强推。
- 行动轨迹和计划状态联动。

设计原则：

- 计划是模型辅助状态，不是后端阶段流。
- 普通问答不应该自动创建计划。
- 用户可以随时打断和改变方向。

### 3.4 v1.0.5 以后：谨慎探索代码写能力

目标：

```text
在 CodeAsk 已经具备可信证据链和权限边界后，再考虑低风险代码写辅助。
```

可能从低风险能力开始：

- 生成修复建议。
- 生成 patch 草稿，但不自动应用。
- 生成验证步骤。
- 生成测试建议。
- 管理员或高级权限用户确认后，才允许写入隔离分支或 worktree。

设计原则：

- 默认仍然只读。
- 写操作必须强确认。
- 写操作必须隔离。
- 写操作必须可回滚。
- 不允许模型默认执行任意 shell。

## 4. 对 Claude Code 的借鉴边界

CodeAsk 应该学习：

```text
模型主导
工具化能力
边界保护
上下文预算
可回放轨迹
用户确认
长期任务推进
```

CodeAsk 不应该照搬：

```text
什么都能执行
什么文件都能改
什么任务都能接
把通用 coding agent 能力塞进问题定位产品
```

## 5. 实施约束

后续版本规划必须遵守以下约束：

1. v1.0.2 先完成 Agent harness，不在同一版本里扩展过多高级能力。
2. 每个后续能力都必须先写 PRD / SDD / plan，再进入代码。
3. 任何写操作、删除操作、知识沉淀操作都必须有用户确认。
4. 任何代码相关能力都必须标注 repo/ref/commit 或默认版本不确定性。
5. UI 展示真实行动轨迹，不展示伪造的后端阶段结论。
6. 工具能力增加时，必须同步增加工具契约、审计和测试。
7. 不允许为了追求“像 Claude Code”而牺牲 CodeAsk 的垂直产品定位。

## 6. 当前结论

v1.0.2 的任务不是“复刻 Claude Code”，而是把 CodeAsk 的 Agent 底座扶正。

正确路线是：

```text
先做对 Agent harness
→ 再增强上下文和记忆
→ 再增强复杂调查计划
→ 最后谨慎探索代码写能力
```

只要 harness 做对，后续逐步接近 Claude Code 的高级 Agent 体验是可行的；如果继续沿用固定状态机，再叠加多少功能都会继续失控。
