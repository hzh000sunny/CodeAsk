# v1.0.2 Agent 会话运行时设计

> 日期：2026-05-07
> 状态：草稿，等待用户审阅
> 范围：v1.0.2 LLM Agent 优化专项

## 1. 产品定位

CodeAsk 不是传统意义上的 LLM Wiki。传统 LLM Wiki 的核心能力通常是“检索知识库，然后基于知识库给出答案”。CodeAsk 的目标更进一步：在垂直研发领域里，把团队 Wiki、已验证的问题定位报告、会话附件、特性元数据和代码仓库组织到同一个 Agent 会话中，让用户通过自然语言多轮沟通逐步得到可信结论。

因此，CodeAsk 首先必须是一个正常的 Agent 聊天产品。用户可以只问一个概念问题，也可以上传日志、补充环境、追问细节、逐步扩大问题范围。Agent 应该围绕用户当前问题自然回答、追问和调用工具，而不是因为用户发了一句话就强制跑完一条固定排障流水线。

当前 v1.0 的默认链路是：

```text
ScopeDetection
→ KnowledgeRetrieval
→ SufficiencyJudgement
→ CodeInvestigation
→ AnswerFinalization
```

这条链路作为早期排障流程建模有价值，但不适合作为每条普通消息的默认会话行为。它的问题是后端替模型做了过多决策：先判断特性，再检索知识库，再判断是否足够，再决定是否查代码。这会导致基础问答能力被破坏，也会让用户感觉系统不再是在聊天，而是在强制执行一套固定流程。

v1.0.2 的方向是：

```text
后端负责注入上下文、提供工具、执行边界校验、记录审计轨迹。
模型负责判断下一步动作：回答、追问、查 Wiki、读报告、读附件、查代码或建议生成报告。
```

## 2. 核心原则

1. 正常聊天优先。普通问题不能自动触发完整调查闭环。
2. RAG 是知识增强层，不是后端决策引擎。
3. 特性是候选上下文，不是用户提问前必须绑定的条件。
4. Wiki、报告、附件和代码都是默认可读的调查能力。
5. 后端只做边界保护，包括路径、仓库、版本、权限、写操作和结果截断。
6. 模型基于上下文和工具能力决定下一步动作。
7. UI 只展示真实发生的 Agent 行动，不展示后端阶段结论。
8. 多轮澄清是基础能力，不是异常兜底。
9. 代码检索不需要默认授权，但需要处理仓库范围和版本不明确的问题。
10. 写操作、删除操作和知识沉淀操作必须由用户确认或通过明确 UI 动作触发。

## 3. 选定方案

v1.0.2 选定方案是 **统一 Tool-Calling Chat Runtime**。

不采用的方案：

- 保留旧状态机作为默认会话：会继续让后端流程覆盖模型判断，根因不变。
- 做“普通聊天 / 深入调查”显式模式切换：会增加用户理解成本，也容易把产品复杂度暴露给用户。

选定后的主链路是：

```text
用户消息
→ 上下文组装
→ 轻量召回
→ Prompt 策略注入
→ LLM 工具循环
→ 工具边界校验
→ 行动轨迹 / 证据记录
→ 模型回答
```

旧的 `ScopeDetection / SufficiencyJudgement / CodeInvestigation` 不再作为默认后端阶段驱动会话。它们有价值的部分会迁移为：

| 旧阶段 | v1.0.2 中的新位置 |
|---|---|
| ScopeDetection | 候选特性召回上下文 |
| KnowledgeRetrieval | 每轮轻量 RAG 召回 + 模型可调用 Wiki/报告工具 |
| SufficiencyJudgement | Prompt 策略，由模型判断证据是否足够 |
| CodeInvestigation | 默认可读的代码工具能力 |
| AnswerFinalization | 模型自然回答策略 |

## 4. 运行时架构

### 4.1 Context Assembler

`Context Assembler` 为每个 assistant turn 组装模型输入。

输入内容包括：

- 当前用户消息。
- 最近多轮会话历史或会话摘要。
- 当前会话附件列表、附件摘要和日志线索。
- 用户在会话中明确过的约束：repo、branch、tag、commit、特性、环境、时间范围、服务名等。
- 轻量召回得到的候选特性。
- 轻量召回得到的 Wiki 片段和已验证报告片段。
- 候选仓库、默认 ref、当前 checkout 信息。
- 当前可用工具列表和工具使用规则。

`Context Assembler` 不做以下判断：

- 不判断“这个问题属于哪个特性”。
- 不判断“知识库是否足够”。
- 不判断“下一步是否必须查代码”。
- 不替模型决定是否追问用户。

它只把模型做判断所需的上下文整理清楚。

### 4.2 轻量召回

每轮用户消息默认执行轻量知识召回。

默认召回范围：

```text
候选特性：top 3
Wiki 文档片段：top 5
已验证报告片段：top 3
```

召回输入：

- 当前用户消息。
- 最近会话摘要。
- 附件摘要和日志关键字。
- 用户提到的特性名、目录名、文件名、错误码、模块名、服务名、接口名。

召回输出只是候选上下文，不能生成流程结论。禁止把这类内容作为后端判断展示给用户：

```text
matched feature alias
insufficient
next_step = code_investigation
范围判断：6
下一步：代码调查
```

如果召回不到内容，只能把“没有高相关召回结果”作为上下文交给模型。是否查代码、是否追问、是否直接回答，由模型决定。

### 4.3 Prompt Policy Injection

v1.0.2 的 prompt 注入应表达产品行为规则，而不是固定阶段流程。

建议注入的核心规则：

- 先回答用户当前问题，不主动扩散到完整排障流程。
- 如果当前问题可以直接回答，就直接回答。
- 如果使用了 Wiki、报告、附件或代码证据，必须说明证据来源。
- 如果证据不足，应追问当前最关键的缺失信息，而不是一次性问一堆问题。
- 如果问题涉及真实实现、配置默认值、接口字段、错误根因或版本差异，可以使用代码工具。
- 如果仓库或版本不明确，应先根据上下文推断；推断不了再追问。
- 如果用户也不知道版本，可以使用系统配置的当前代码或默认分支，但必须标注不确定性。
- 不要向用户暴露内部阶段名，例如 `ScopeDetection`、`SufficiencyJudgement`。
- 不要因为存在代码工具就默认查代码。
- 不要因为召回到某个特性就强行把会话绑定到该特性。

### 4.4 LLM Tool Loop

模型接收工具定义，并决定是否调用工具。

后端职责：

- 校验工具名和参数 schema。
- 校验文件路径和仓库边界。
- 解析 repo/ref/commit。
- 处理权限和写操作确认。
- 截断、摘要和结构化工具结果。
- 将工具错误结构化返回给模型。
- 记录工具调用、证据和行动轨迹。

后端不负责：

- 决定模型下一步该查什么。
- 决定当前证据是否足够。
- 决定是否必须进入代码调查。
- 决定是否应该结束回答。

### 4.5 工具边界校验

只读工具默认可用。写操作、删除操作、报告生成和 Wiki 沉淀操作必须由用户确认。

工具失败时，不应直接让整轮会话失败。优先把错误结构化返回给模型，让模型自然追问或解释当前限制。

示例：

```json
{
  "ok": false,
  "error_type": "needs_clarification",
  "message": "无法确定要读取哪个仓库。",
  "suggested_user_question": "你希望我查看哪个仓库或分支？如果你也不清楚，我可以先按默认仓库和默认分支做初步判断。"
}
```

## 5. 上下文分层

v1.0.2 需要把“给模型什么信息”设计清楚，否则模型会在过多噪音里失控。

建议上下文分层：

```text
L0 系统规则
L1 工具能力说明
L2 会话历史和当前用户输入
L3 用户显式约束
L4 轻量 RAG 召回结果
L5 附件摘要和日志线索
L6 候选代码范围
L7 已执行工具结果
```

### 5.1 上下文预算

上下文注入必须有预算控制。

建议初始策略：

- 系统规则保持短而稳定。
- 会话历史优先保留最近轮次，过长时生成摘要。
- Wiki 和报告召回只注入片段，不注入全文。
- 附件默认注入摘要，不注入完整大文件。
- 代码工具结果默认摘要 + 精确引用，必要时模型再读文件片段。
- 单个工具结果必须有字符上限，避免一次调用撑爆上下文。

这部分是本次二次审视补充出来的关键点：如果只说“全部放入上下文”，实际实现会因为 token 预算失控而不稳定。正确做法是把“候选信息”压缩注入，把“完整内容”作为工具按需读取。

## 6. 工具模型

### 6.1 默认只读工具

模型可以直接调用以下只读工具，不需要用户额外授权：

```text
search_wiki
read_wiki_node
search_reports
read_report
list_session_attachments
read_session_attachment
search_code
read_code_file
inspect_repo_tree
```

代码读取是 CodeAsk 的核心增强能力，不应该默认要求用户确认“是否允许读取代码”。需要处理的是代码范围和版本是否明确。

### 6.2 代码范围和版本解析

当模型需要查代码时，仓库和版本按以下优先级解析：

1. 用户在当前会话中明确指定的 `repo + branch/tag/commit`。
2. 候选特性关联仓库的默认 ref。
3. 全局仓库池中的默认仓库和默认 ref。
4. 后端登记的本地仓库当前 checkout。
5. 仍无法确定时，向用户追问仓库范围。

如果用户不知道具体版本，模型可以继续使用当前代码或默认分支，但工具结果和最终回答都必须明确标注：

```text
代码证据基于当前配置的默认代码版本，可能与实际故障版本不一致。
```

### 6.3 需要确认的写操作

以下动作不能由模型静默执行：

```text
generate_report
promote_to_wiki
write_wiki
rename_wiki
delete_wiki
clear_wiki_directory
change_session_title
delete_session
```

模型可以建议执行这些动作，但后端必须要求用户确认，或者只响应用户明确点击的 UI 操作。

### 6.4 工具结果规范

工具结果至少应包含：

```text
ok
tool
summary
evidence_refs
version_info（代码工具需要）
warnings
error_type（失败时）
suggested_user_question（需要澄清时）
```

这样模型可以稳定地把工具结果转成自然语言，而不是直接暴露底层异常。

## 7. 会话行为

v1.0.2 的 Assistant 应支持以下自然响应模式。这些是模型策略，不是后端状态机。

| 响应模式 | 使用场景 |
|---|---|
| 直接回答 | 问题可以从模型自身、会话上下文或召回知识中回答 |
| 追问澄清 | 缺少关键环境、版本、范围、现象或日志 |
| 证据化分析 | Wiki、报告、附件或代码证据已经支持具体判断 |
| 调查建议 | 当前信息不足，但可以继续查 Wiki、附件或代码 |
| 报告 / Wiki 建议 | 问题已经基本定位，或用户希望沉淀知识 |

模型不应该因为工具存在就把所有工具跑一遍。每轮回答应贴近用户当前输入。

示例行为：

- 用户问“这个配置是什么意思？”：优先解释配置；如 Wiki 有明确说明，可引用 Wiki。
- 用户问“这个报错是什么原因？”：可先结合 Wiki、报告和日志摘要回答；必要时查代码。
- 用户只给一段日志但没有现象：先提炼日志线索，再问最关键的上下文。
- 用户问“帮我定位根因”：可以更积极地使用 Wiki、报告、附件和代码工具，但仍需要标注证据和不确定性。

## 8. 特性处理

用户不应该在提问前绑定特性。

特性在 v1.0.2 中的角色：

- 作为 RAG 召回候选。
- 作为 Wiki 一级空间的组织维度。
- 作为仓库关联和分析策略的辅助上下文。
- 作为生成报告或沉淀 Wiki 时需要确认的归属。

UI 可以低打扰展示候选特性，例如：

```text
可能相关：小米、订单、支付
```

用户可以无视，也可以主动纠正或限制范围。只有在以下场景需要明确确认特性：

- 生成问题定位报告。
- 将会话内容晋级为 Wiki。
- 写入或修改某个特性空间下的知识。
- 候选特性冲突导致模型无法继续判断。
- 用户明确说“只看某个特性”。

跨特性问题是合法输入。模型应说明可能涉及哪些方向，而不是过早强行绑定单一特性。

## 9. UI 和事件模型

### 9.1 行动轨迹替代调查进度

右侧调查区域应改为可折叠的 **Agent 行动轨迹**。

展示真实发生的事实：

- 已参考哪些 Wiki 文档。
- 已参考哪些已验证报告。
- 候选特性有哪些。
- 调用了哪些工具。
- 读取了哪些代码文件。
- 代码证据来自哪个 repo/ref/commit。
- 是否使用了默认代码版本。
- 哪些信息需要用户补充。
- 工具失败的原因。

不再展示固定流程结论：

```text
范围判断
充分性判断
下一步：代码调查
insufficient
matched feature alias
```

### 9.2 SSE 事件方向

v1.0.2 推荐事件：

```text
text_delta
retrieval_context
tool_call
tool_result
evidence
assistant_action
needs_clarification
done
error
```

旧事件可以为了兼容暂时保留，但默认 UI 不再把它们渲染成固定阶段：

```text
stage_transition
scope_detection
sufficiency_judgement
```

示例 `retrieval_context`：

```json
{
  "feature_candidates": [
    {"name": "小米", "score": 0.91}
  ],
  "wiki_hits": [
    {"title": "小米病历", "path": "小米 / 知识库 / 小米病历", "score": 0.82}
  ],
  "report_hits": []
}
```

示例 `tool_result`：

```json
{
  "tool": "read_code_file",
  "status": "ok",
  "summary": "读取 src/example.py",
  "version": {
    "repo": "example",
    "ref": "main",
    "status": "default_or_current"
  },
  "warnings": [
    "代码证据基于默认分支，未确认线上故障版本。"
  ]
}
```

## 10. 数据记录和审计

每个 assistant turn 应记录：

```text
turn_id
session_id
user_message_id
assistant_message_id
retrieval_context
tool_calls
evidence_refs
code_version_refs
clarification_requests
model_config_id
final_answer
```

审计目标：

- 能回放模型看到过哪些上下文。
- 能回放模型调用过哪些工具。
- 能区分 Wiki、报告、附件和代码证据。
- 能看到代码证据的 repo/ref/commit。
- 能标记“明确版本”和“默认当前代码”的差异。
- 不伪造后端已经验证模型推理正确。

这部分也是 v1.0.2 的关键补充：我们需要记录模型“看到了什么”和“做了什么”，但不能把旧的后端阶段判断当成事实审计结果。

## 11. 迁移策略

v1.0.2 不应该在旧状态机上继续打补丁。建议新增独立运行时模块，再逐步切换默认会话入口。

建议迁移顺序：

1. 新增 `Agent Chat Runtime` 模块，先不删除旧 runtime。
2. 增加 deterministic mock LLM 测试，覆盖工具调用、追问和直接回答。
3. 会话发送接口增加新 runtime 路径，默认切到新 runtime。
4. 旧 SSE 事件保留兼容，但前端默认消费新行动轨迹事件。
5. 前端移除固定调查进度展示，改为 Agent 行动轨迹。
6. 文档标注 v1.0 固定状态机是历史设计，不再是 v1.0.2 默认会话模型。
7. 稳定后再考虑删除旧默认流程或只保留为内部评测基线。

迁移过程中必须保护 v1.0.1 已完成能力：

- Wiki 工作台。
- Wiki 导入、编辑、排序、来源治理。
- 特性管理。
- 报告生成、验证和投影。
- 设置和 LLM 配置。

## 13. 验收标准

1. 普通问答不会触发完整固定调查链路。
2. 每轮默认执行轻量 Wiki / 报告 / 特性候选召回，并注入上下文。
3. 候选特性不会强制绑定会话。
4. Wiki 足够回答的问题不会出现不必要代码读取。
5. 模型可以在需要实现细节时默认读取代码。
6. 代码范围和版本解析遵循文档中的优先级。
7. 使用默认分支或当前 checkout 时，行动轨迹和回答都显示版本不确定性。
8. UI 行动轨迹只展示真实动作，不展示固定阶段结论。
9. 默认 UI 不再显示“范围判断”“充分性判断”“下一步代码调查”等标签。
10. 工具错误会作为结构化上下文回到模型，模型能自然追问。
11. 报告生成和 Wiki 写操作仍然需要用户确认。
12. 多轮会话可以逐步补充日志、环境、版本和范围，不会每轮重新跑固定流程。
13. v1.0.1 Wiki、报告、设置、特性管理有回归测试覆盖。
14. 前端刷新、切换会话后，历史行动轨迹和消息显示稳定。
15. mock LLM 测试能覆盖直接回答、追问、Wiki 读取、代码读取、工具错误五类路径。

## 14. 非目标

v1.0.2 不把以下事项作为必须完成项：

- 引入新的向量数据库。
- 重写 Wiki 搜索排序体系。
- 做企业级权限系统。
- 做复杂 agent plan/executor 多智能体框架。
- 做自动代码修改能力。
- 做自动生成并发布正式报告。
- 做 UI 大改版或重新设计整个工作台。

这些能力可以后续规划，但 v1.0.2 的核心是修正默认 Agent 会话运行时。

## 15. 二次审视补充结论

本次从英文版改写为中文版时，补充了以下遗漏：

- 明确“全部注入上下文”不是无限塞全文，而是分层注入和预算控制。
- 明确工具结果需要结构化，方便模型追问和自然解释错误。
- 明确旧 runtime 的迁移策略，避免直接在旧状态机上继续打补丁。
- 明确前端旧事件兼容和新行动轨迹事件的关系。
- 明确审计记录不等于后端验证推理正确，只记录模型看到什么、用了什么。
- 明确 v1.0.2 非目标，避免把检索增强、权限、UI 大改和复杂 agent 框架都塞进本版本。
